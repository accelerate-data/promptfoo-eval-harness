# VD-3796: Fix concurrency.js CJS require('p-limit') under ESM-only p-limit v7 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un-break `npm test` (70 failing, 0 skipped-that-matter) by restoring a CJS-compatible `p-limit` so `require('p-limit')` resolves to the callable default export again — durably, so an unattended dependency bump can't silently reintroduce the same break.

One reviewer directly ran the suite before and after the fix in this worktree and confirmed the true baseline/target counts and two step-level defects below; those fixes are folded in. Full findings are not repeated here — see the conversation record. One reviewer's citation to a `CLAUDE.md` Darwin/`@swc` lockfile-drift note was checked and found to be fabricated (no such note exists in this repo) — the citation was discarded, but the underlying "check your lockfile diff" practice was kept because it's cheap and correct on its own merits.

**Architecture:** Downgrade the `p-limit` dependency from `^7.3.0` back to `^3.1.0` — the last CJS-compatible major, and the exact version this package was pinned to before the breaking bump (commit `ccc92fd`, 2026-05-31, PR #26). This is a pure dependency-version revert: no source file changes, no call-site changes, no API-shape changes, because v3.1.0's `pLimit(concurrency)` default-export-as-callable-function contract is exactly what every existing call site (`concurrency.js`, `dir-walk.js`, `bench/parallel-throughput/driver.js`, `dir-walk.test.js`) already assumes and was written against pre-bump.

**Tech Stack:** Node.js (CJS, no `"type": "module"` in `package.json`), npm, `node --test`.

## Global Constraints

- `package.json` has no `"type": "module"` — the whole package is CJS. Do not add one as part of this fix.
- Per `AGENTS.md`: adding/changing a runtime dependency requires updating both `package.json` and `templates/package.json` if consumers also need it at runtime. `templates/package.json` does **not** list `p-limit` as a direct dependency (confirmed: it only lists `@accelerate-data/promptfoo-eval-harness`, `js-yaml`, `promptfoo`) — so no template change is required for this fix.
- `npm test` runs `scripts/*.test.js` and `scripts/framework/*.test.js` — this is the verification gate. **Verified true counts (a reviewer ran the suite directly in this worktree):** baseline is `70 fail / 413 pass / 2 skipped`; the fixed target is `0 fail / 483 pass / 2 skipped`. The 2 skipped tests are pre-existing and unrelated to this fix — do not try to make them pass, and do not treat "485 passing" as the target (485 = 483 + 2 skipped, not 485 passing).
- No `p-limit` v7-only feature (`activeCount`, `pendingCount`, `clearQueue`, per-task `signal`, etc.) is used anywhere in this codebase (verified by grep across `scripts/framework/concurrency.js`, `scripts/framework/dir-walk.js`, `bench/parallel-throughput/driver.js`, `scripts/framework/dir-walk.test.js`) — so downgrading loses no functionality currently in use.
- `.github/dependabot.yml` currently has no `ignore` rules for npm deps, and the original break (commit `ccc92fd`, PR #26) was itself an unattended dependabot semver-major bump. Without an ignore rule, dependabot will reopen the identical major-version bump on its next weekly scan and reintroduce this exact failure — so this fix is incomplete without one. See Task 2.

## Why downgrade instead of dynamic `import()`

The repo's established ESM-interop pattern (`docs/design.md`, `codex_sdk`/`opencode_sdk` providers) is `await import(...)` inside an async `init()`. That doesn't fit here: every `p-limit` call site (`concurrency.js`, `dir-walk.js:202`, `bench/parallel-throughput/driver.js`) is synchronous today and uses the returned `LimitFunction` in the same tick — converting would force every caller in those chains to become `async` for no behavioral gain, a disproportionate blast radius for a dependency-version bugfix. v3.1.0 already provides everything currently used (Global Constraints, above), so downgrade is the minimal fix. This is a deliberate, revisitable tradeoff, not an oversight — Task 1 Step 2 leaves a code comment saying so, so a future maintainer hitting the next ESM-only dependency bump has a stated rule to apply instead of relitigating this decision from scratch.

### Task 2: Add a dependabot ignore rule so the same major bump can't recur

**Files:**
- Modify: `.github/dependabot.yml`

**Interfaces:**
- Consumes: nothing from Task 1 beyond the fact that `p-limit` is now pinned to `^3.1.0`.
- Produces: a standing guard that prevents dependabot from ever proposing a `p-limit` major bump again without a human first revisiting the Task 1 Step 2 breadcrumb comment.

- [ ] **Step 1: Add an `ignore` rule for `p-limit` majors to the npm update block**

In `.github/dependabot.yml`, under the `package-ecosystem: npm` entry, add an `ignore` list:

```yaml
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
    ignore:
      - dependency-name: "p-limit"
        update-types: ["version-update:semver-major"]
```

This still allows dependabot to propose patch/minor bumps within the `3.x` line, but blocks another silent major bump to an ESM-only version.

Expected output: `valid yaml`, no parse errors.

- [ ] **Step 3: Commit**

```bash
git add .github/dependabot.yml
git commit -m "chore: ignore p-limit semver-major bumps in dependabot

Prevents dependabot from silently reproposing the p-limit v7 (ESM-only)
```
